# 工程代码技术选型

## 项目定位

本子仓从零构建 CertGlance，一款 macOS 原生 TLS 证书到期小组件。系统小组件是主要展示入口；宿主 App 只负责域名管理、主动检查与通知授权，不另造一套完整看板。

## 技术栈与边界

- 目标平台为 macOS 26 起。仅在无需大兼容层时考虑向前兼容；当前工程不承诺旧系统支持。
- 使用 Swift 6、SwiftUI、WidgetKit、Security.framework 与 UserNotifications，不引入第三方依赖。
- 使用正常的 SwiftUI `WindowGroup`、系统 `List`、`Form`、`Button`、`Alert` 和 SF Symbols；不模拟窗口、菜单或系统通知。
- Widget 时间线请求约每 12 小时更新一次，实际执行由 WidgetKit 决定，不承诺准点或每天必达。扩展可在生成时间线时做限时网络检查；手动刷新由宿主 App 发起。
- 通过系统 TLS 信任对象读取叶子证书截止时间，不绕过服务器证书校验，也不把 HTTP 状态当作证书状态。

## 数据与通知

- 域名列表、证书快照、通知去重记录通过共享仓储接口读写。首个适配器使用 App Group `UserDefaults`；这是功能开发态方案，**不代表 Mihomo Meter 式自签名分发已可用**。
- 当前 Bundle ID `com.HongXunPan.SSLWidget` 与 App Group ID `group.com.HongXunPan.SSLWidget` 为开发态占位；正式分发前须确认稳定身份并验证迁移及共享访问。
- 宿主 App 请求通知权限。每次成功读取证书后，根据截止时间规划默认 30／7／1 天本地提醒；已进入提醒窗口的首次检查仅提醒一次。同一证书截止时间与同一提醒档位去重。
- 扩展按时间线更新快照及提醒；若系统不运行时间线、用户关闭通知、共享容器不可用，提醒无法保证准时。应用启动及主动检查会重新同步。
- 用户可从看板看到检查时间、连接失败、证书不受信任和已过期状态。失败时保留已知截止时间，不把网络失败误报成健康。

## 默认执行规则

- 本项目代码实现使用 `macos-native-ui-engineer`，涉及视觉时同时使用 `ui-ux-pro-max`；系统语义与 Apple 官方文档优先于通用 Web 或移动端模板建议。
- 最小验证：`plutil -lint` 检查工程与 plist；`xcrun swift format lint --recursive --strict` 检查 Swift；`xcodebuild` 做 macOS 无签名构建。构建不能代替安装、WidgetKit 调度、App Group 权限或系统通知验收。
- 若官方 API、证书链、扩展沙盒、共享存储、签名身份与代码前提冲突，立即停止并重新规划，不静默添加兜底或将静态通过宣称为运行态通过。

## 分发边界

后续分发遵循 Mihomo Meter 的规则方向：固定自签名身份、按架构提供 DMG、GitHub Releases 与 Sparkle 更新；不复用其 Bundle ID、证书或更新密钥。

当前仅为独立假数据文件桥接 PoC 提供手动 GitHub Actions：使用 SSL Widget 专用固定自签名证书、签名宿主、Widget 与短时独立修复助手，生成非公证 DMG 及静态核验报告。该工作流不发布 GitHub Release，不为正式应用签名，也不引入 Sparkle；DMG 拖拽安装必须继续保留，不以 Sparkle 作为唯一升级路径。版本 2 的宿主写入、Widget 读取，以及版本 3 的 Widget 写回、宿主核对，均已由用户在自签名安装后实机确认。版本 3→4 和 4→5 拖拽实测均发现旧扩展进程驻留：宿主启动时请求刷新不足以换用新扩展，定点结束旧扩展后才得到新构建回执。父仓版本 5 手工脚本只供本机 PoC，不打入 DMG。版本 6 的首次启动短时助手修复已由用户在本机确认可使组件变为版本 6，但不证明其他机器或正式应用也可靠。版本 7 在 Widget 时间线运行时只读比较自身进程与 `/Applications` 安装包构建，作为后续不打开宿主的覆盖实验；Widget 侧不唤起助手，原有的宿主启动修复保持不变。这些结果不能证明正式应用的分发与共享链路可用。正式应用目前仍使用开发态 App Group 仓储，迁移需要另行确认范围与验收口径。

后续构建 6／7 的 Finder 覆盖实验还出现另一类故障：系统注销 Widget 扩展并从存储中移除原桌面组件；打开宿主只恢复扩展登记和图库入口，没有恢复桌面位置。因此当前拖拽覆盖升级未通过验收，不能把构建 6 的旧进程修复成功推广到组件实例已被移除的场景。受控升级候选、签名与沙盒可行性、桌面位置保留的硬验收见 [PoC 升级分发验证](../PoC/WidgetSharing/升级分发验证.md)；Sparkle 等候选尚未实现或证明有效。

构建 8 已由手动 GitHub Actions 在提交 `49cd498` 上签名打包。父仓本机脚本以同卷暂存和系统 `FileManager.replaceItem` 做了一次构建 7→8 受控替换：原桌面小组件未丢失；启动构建 8 宿主后，真实回执与页脚均为 8/8；退出宿主并弹出两份测试 DMG 后，用户仍确认原位置显示 8/8。这只是一台 Mac 上的一次 PoC 验收，不是普通用户可用的更新入口，也不能推断 Finder 拖拽覆盖已修复或不打开宿主即可完成运行态更新。正式 CertGlance 的 App Group 分发与迁移仍未验证，Sparkle 暂不启用。

手动工作流另提供显式的“无助手诊断包”开关：仅在无签名构建完成后、正式签名前，从假数据 PoC 宿主包中移除嵌入的 Helper；宿主和 Widget 源码、Bundle ID 与专用签名身份不变。默认候选仍嵌入助手。诊断包只用于 Finder 覆盖后、启动宿主前观察原桌面组件是否保留；它不是正式更新包，不能用单次保留结果认定助手嵌入就是根因。

构建 9 仅在独立假数据 PoC 的现有短时 Helper 中增加显式受控安装模式：只读预检、固定安装位置、同证书及递增构建核对、同卷暂存和系统 `FileManager.replaceItem` 替换；不新增 Helper target、自动提权或后台更新，不启用 Sparkle。当前只通过 plist、Swift 格式和无签名构建检查，尚未对构建 9 自签名 DMG 与原桌面组件位置做运行态验收；普通用户更新交互及正式应用分发均未完成。
