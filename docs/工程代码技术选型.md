# 工程代码技术选型

## 项目定位

本子仓从零构建 CertGlance，一款 macOS 原生 TLS 证书到期看板。桌面小组件负责快速浏览；宿主 App 提供完整的多端点可视化看板、管理、主动检查与通知授权。看板内容采用系统 SwiftUI 容器、Gauge、SF Symbols 与语义颜色，不模拟 watchOS 窗口或 macOS 系统控件。

## 技术栈与边界

- 目标平台为 macOS 26 起。仅在无需大兼容层时考虑向前兼容；当前工程不承诺旧系统支持。
- 使用 Swift 6、SwiftUI、WidgetKit、Security.framework 与 UserNotifications，不引入第三方依赖。
- 使用正常的 SwiftUI `Window`、系统 `List`、`Button`、`Alert` 和 SF Symbols；不模拟窗口、菜单或系统通知。
- Widget 预排未来七天内的剩余天数变化条目，组件同时展示剩余天数与到期日期；约每 12 小时请求一次新时间线，实际执行由 WidgetKit 决定，不承诺准点或每天必达。自动检查仅纳入距上次尝试至少 12 小时的域名；扩展每次至多从优先队列派发六个，未检查完时请求约一小时后继续。手动刷新仍检查全部域名，但也按同一队列顺序派发。
- 队列先处理从未检查的域名，再处理距上次尝试至少 24 小时的域名，其余已到检查时间的域名按有上限的风险分数排序；同档同分按最久未检查、域名稳定排序。已过期／一日内／七日内／三十日内分别加 60／45／30／15 分，不受信任加 20 分；连续失败一次加 10 分、两次及以上固定加 18 分；距最近一次成功读取证书至少一／三／七天分别加 6／12／18 分，从未成功同样只加 18 分。不受信任但已读取证书算探测成功并清零连续失败；失败保留上次成功时间和已知截止时间。24 小时是排序门槛，不是系统调度时限；失败不会触发额外的即时自动重试。
- 通过系统 TLS 信任对象读取叶子证书截止时间，不绕过服务器证书校验，也不把 HTTP 状态当作证书状态。
- 监控对象为 HTTPS 主机与端口；443 保持历史域名标识，其他端口使用 `域名:端口` 独立标识。输入可粘贴域名、`域名:端口` 或带路径的 HTTPS URL；无显式端口的 HTTP URL 仅提取主机并转为 HTTPS 443 检查，带显式端口的 HTTP URL 拒绝，避免把明文端口误认为 TLS 端口。证书检查仅连接所提取端点，不跟随 HTTP 跳转读取其他端点的证书。旧 JSON 缺少端口时按 443 读取。

## 数据与通知

- 域名列表、证书快照、通知去重记录通过共享仓储接口读写。正式候选使用项目专用文件桥接：宿主读写 `~/Library/Application Support/com.HongXunPan.CertGlance/`，Widget 仅 `config/` 只读、`state/` 读写；JSON 原子落盘，跨进程写入以文件锁串行化。临时沙盒文件例外虽有独立假数据 PoC 支撑，正式 App 仍须安装后单独验收，不视为 Apple 长期承诺的共享能力。
- 正式候选宿主 Bundle ID 为 `com.HongXunPan.CertGlance`，Widget Bundle ID 为 `com.HongXunPan.CertGlance.Widget`，不声明 App Group。先前开发态 `com.HongXunPan.SSLWidget` 的 App Group 数据未迁移；此前没有已发布的正式版本，若本机曾运行开发态版本，需要手动重新添加域名。
- 宿主 App 请求通知权限。每次成功读取证书后，根据截止时间规划默认 30／7／1 天本地提醒；已进入提醒窗口的首次检查仅提醒一次。同一证书截止时间与同一提醒档位去重；同步时重新读取当前仓储，避免已删除域名的旧检查结果重新安排提醒。
- 扩展按时间线更新快照及提醒；若系统不运行时间线、用户关闭通知、文件桥接不可用，提醒无法保证准时。应用启动及主动检查会重新同步。
- 用户可从宿主看板和小组件看到剩余天数与到期日期，以及连接失败、证书不受信任和已过期状态；宿主看板还展示检查时间及总体状态。30 天窗口 Gauge 只表达距到期日的短期距离，不代表证书完整有效期。失败时保留已知截止时间，不把网络失败误报成健康。

## 默认执行规则

- 本项目代码实现使用 `macos-native-ui-engineer`，涉及视觉时同时使用 `ui-ux-pro-max`；系统语义与 Apple 官方文档优先于通用 Web 或移动端模板建议。
- 最小验证：`bash scripts/check-certglance.sh` 检查工程、plist、Swift 格式、模型与文件仓储；`xcodebuild` 做 macOS 无签名构建。构建不能代替安装、WidgetKit 调度、沙盒文件例外或系统通知验收。
- 若官方 API、证书链、扩展沙盒、共享存储、签名身份与代码前提冲突，立即停止并重新规划，不静默添加兜底或将静态通过宣称为运行态通过。

## 分发边界

后续分发遵循 Mihomo Meter 的规则方向：固定自签名身份、按架构提供 DMG、GitHub Releases 与 Sparkle 更新；不复用其 Bundle ID、证书或更新密钥。

独立假数据文件桥接 PoC 的手动 GitHub Actions 继续用于升级机制诊断。正式 CertGlance 新增独立的手动打包工作流：同一项目专用自签名证书签名正式宿主与 Widget，生成双架构非公证 DMG、校验和与静态报告；不嵌入 PoC 助手、不启用 Sparkle、不自动发布 GitHub Release。DMG 拖拽保留为**首次安装**方式，Finder 拖拽覆盖升级仍未通过验收。假数据 PoC 的构建 2／3 文件共享实测只支持技术可行性判断，不等同正式应用的域名、TLS、通知和视觉运行态通过。

后续构建 6／7 的 Finder 覆盖实验还出现另一类故障：系统注销 Widget 扩展并从存储中移除原桌面组件；打开宿主只恢复扩展登记和图库入口，没有恢复桌面位置。因此当前拖拽覆盖升级未通过验收，不能把构建 6 的旧进程修复成功推广到组件实例已被移除的场景。受控升级候选、签名与沙盒可行性、桌面位置保留的硬验收见 [PoC 升级分发验证](../PoC/WidgetSharing/升级分发验证.md)；Sparkle 等候选尚未实现或证明有效。

构建 8 已由手动 GitHub Actions 在提交 `49cd498` 上签名打包。父仓本机脚本以同卷暂存和系统 `FileManager.replaceItem` 做了一次构建 7→8 受控替换：原桌面小组件未丢失；启动构建 8 宿主后，真实回执与页脚均为 8/8；退出宿主并弹出两份测试 DMG 后，用户仍确认原位置显示 8/8。这只是一台 Mac 上的一次 PoC 验收，不是普通用户可用的更新入口，也不能推断 Finder 拖拽覆盖已修复或不打开宿主即可完成运行态更新。正式 CertGlance 使用文件桥接，其签名安装运行态仍需独立验收；Sparkle 暂不启用。

手动工作流另提供显式的“无助手诊断包”开关：仅在无签名构建完成后、正式签名前，从假数据 PoC 宿主包中移除嵌入的 Helper；宿主和 Widget 源码、Bundle ID 与专用签名身份不变。默认候选仍嵌入助手。诊断包只用于 Finder 覆盖后、启动宿主前观察原桌面组件是否保留；它不是正式更新包，不能用单次保留结果认定助手嵌入就是根因。

构建 9 仅在独立假数据 PoC 的现有短时 Helper 中增加显式受控安装模式：只读预检、固定安装位置、同证书及递增构建核对、同卷暂存和系统 `FileManager.replaceItem` 替换；不新增 Helper target、自动提权或后台更新，不启用 Sparkle。提交 `dd54643` 的手动 Action 已完成自签名 DMG，8→9 受控替换在本机保留原桌面组件；本次不打开宿主的观测中，构建 8 扩展虽读到安装构建 9，桌面仍显示 8／8，启动宿主一次后才确认原位置显示 9／9。此结果只证明本机单次路径，不证明无宿主自动更新、普通用户更新交互或正式应用分发。
